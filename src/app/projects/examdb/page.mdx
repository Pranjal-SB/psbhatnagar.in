# examdb

<p className="cs-meta">2025 · database + api · fastapi · postgres · next.js</p>

A scraper-fed database of Indian entrance-exam dates with confidence-scored
freshness. Official portals bury dates in PDFs; coaching sites bury them in ads.
examdb answers one question in five seconds: *is my exam's date out, and when
does it close?*

## the problem

Indian exam aspirants — JEE, NEET, CET, GATE — check under deadline stress,
mostly on mobile. The dates they need are facts, but every source degrades them:
government portals hide them inside PDFs, aggregators wrap them in ad walls and
lead-capture forms. There was no place that treated the dates themselves as the
product.

## approach

The scrapers are the product. Everything else — API, pipeline, site — is
scaffolding around getting a date onto the page fresh and trustworthy.

- **Dates are the product.** Every surface optimises for scanning dates and
  status; decoration never competes with data.
- **Trust is visible.** Confidence tiers, sources, and freshness are shown, not
  implied.
- **Search first, browse second.** The home page commits to search as the
  five-second action.
- **Density over cards.** Rows, dividers, and tables beat uniform card walls.

## pipeline

A daily run, scheduled by GitHub Actions rather than a long-lived worker:

`scrape → identity/normalise → dedup → observations → reduce → write`

Each exam has a source with a tier (1 = official primary, 2 = secondary/news).
Observations from multiple sources reduce into a single record with a confidence
score, so a date backed by an official portal outranks a date seen only in news.

## stack

- **API** — FastAPI + SQLAlchemy (async) + Postgres.
- **Pipeline** — `pipeline/runner.py`, scheduled daily by GitHub Actions.
- **Frontend** — Next.js.
- **Monitoring** — Prometheus metrics at `/metrics`.

## what it taught me

Coverage and drift are the real work: every exam needs a working source, and
parsers rot as government sites change under them. The interesting engineering
wasn't the framework — it was making stale data visibly stale.
